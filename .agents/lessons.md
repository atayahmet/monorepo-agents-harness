# Lessons — monorepo-agents-harness (repo root)

- The artifact filenames are a **contract**: `memory-gate.sh`, the index format, adapter build
  hooks, the review skill and the docs all reference `1_plan.md` / `2_spec.md` by name. Any rename
  must touch every consumer of that name in the same commit.
- Backcompat is cheaper than migration for a shared template: keep the gate/consumers accepting the
  old `2_spec.md` as a spec when `1_spec.md` is absent, so installed projects with in-flight tasks
  are not broken by an upgrade.
- The `1_`/`2_` numeric prefix means "phase order", not just a cosmetic index — reordering the files
  means reordering *when the agent writes them* (spec before plan), which also flips what the
  pre-implementation prior-art search gates on.
- Every root-facing template shipped under `core/` must mirror the `AGENTS.md` install path: if
  `core/root-*.md` is meant to land at the target root, `install-harness.sh` step 3 must write it
  (with provenance marker), not just ship it in the bundle. The `--sync-only` update path never
  writes root files — document that so users know when a fresh root file will or won't appear.
- Parallel checks in `audit-install.sh` (one per root file) are the safety net that turns "silently
  never installed" into a named gap. Removing/clarifying a doc's "optional copy it yourself" prose
  must come in the same commit as the automation, or the two drift.
- A conditional gate is kinder than a universal one for shared templates: making intent approval
  mandatory *only* for intent-seeded tasks (`0_intent.md` present) preserves the ad-hoc fast path
  while still guaranteeing the intent chain when one exists. If build had demanded an approved intent
  for every task, it would have contradicted `-spec`'s lenient ad-hoc path and broken valid ad-hoc
  workflows at the last gate.
- Runtime workflow validation belongs in `core/scripts/` (a `task-state.sh` mirroring `memory-gate.sh`'s
  plain grep/awk frontmatter parsing) — not in adapter command prose and not in a text-searchable
  status file. Stage commands stay thin: they shell out to the validator, handle the one
  adapter-specific concern (plan-mode detection), and delegate writing to the shared skill.
- Memory auto-generated by `-build` must be written *after* the implementation commits land so the
  `commits:` field is populated — the existing "memory after commit" rule in `agent-workflow` Phase 3
  carries over unchanged when build takes over the write.
- An agent-neutral operation (like "update the harness") should not carry a per-adapter entry point
  when a paste-in README prompt plus the shared skill covers it — the update check used to be a
  per-adapter command/skill on all three adapters, and removing it cut three files + three manifest
  rows while keeping the exact same workflow reachable from any agent. Before adding a slash command,
  ask whether a shared-skill + README-prompt path would serve users just as well and with less
  surface to keep in sync across adapters.
- Removing an entry point is manifest-only for consumers: `refresh` re-applies rows (idempotent) but
  does not delete files the new manifest no longer lists, so a consumer keeps a stale
  `/monorepo-harness:update` until it removes or refreshes it. The CHANGELOG Upgrade Note must say
  that plainly (re-running refresh clears it; the stale file is harmless because it only points at
  the still-valid shared skill), and `audit-install.sh --against <new release>` will flag the extra
  file — expected, not a regression.
